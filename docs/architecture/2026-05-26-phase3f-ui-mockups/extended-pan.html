Extended pan: DDC center + wideband context as ONE pan

Your idea reframes wideband. It's not a separate pan type — it's what you see when you zoom a DDC pan out past its native ~1.5 MHz bandwidth. The listenable region stays in the middle, wideband fills the wings.

The concept in one sentence

A DDC pan normally shows ±768 kHz of listenable I/Q. When the operator zooms out past that, instead of stretching the I/Q trace or going blank, the pan starts rendering wideband data on the wings while keeping the high-resolution I/Q trace in the center. One pan, two data sources, smooth zoom-out into context.

In effect: every DDC pan becomes a wideband pan when you zoom out far enough. No mode switching. No separate pan type. Just a continuous zoom gesture from "I'm working this signal" to "where else is action on this antenna?"

What happens when you click in each region

Click behavior follows region type
Click inside listenable region (DDC's ±768 kHz):
  → Slice retunes to that frequency within the existing DDC. No DDC change. Click-and-listen, no latency.

Click outside listenable region (wideband wing):
  → DDC center retunes to that frequency. The "listenable island" jumps to the clicked position.
  → Wideband wings reflow around the new center.
  → Slight delay (DDC retune is a wire command, takes ~50-100 ms).

Visual indicator — the listenable region has:
  • Brighter spectrum trace (full opacity, sharp)
  • Dashed vertical boundary lines on left + right edges
  • Slightly different background tint (subtle, not in-your-face)
  • Hover cursor changes from pointer to crosshair inside, normal arrow outside

Why this is better than wideband-as-a-separate-pan

Separate wideband pan (what I proposed earlier)
• Two pan types (DDC pan, Wideband pan)
• Operator decides per pan slot which type to use
• "12h" layout has 1 wideband + 2 DDC
• Mental model: 2 different things sharing the screen
• Workflow: glance at wideband strip → click → focus shifts to DDC pan below
• CPU cost: separate FFT pipelines for each
Extended pan (your idea)
• One pan type — DDC pan with optional wideband extension
• Operator just zooms; transition is implicit
• Any layout (1, 2v, 2h, 2x2) works with extended pans
• Mental model: "one window into the spectrum, more or less zoomed"
• Workflow: zoom out → see context → click → zoom back in stays where I clicked
• CPU cost: same (wideband + DDC FFT both running), but no pan-mode-switch UI surface

Tradeoffs to be honest about

● Alex BPF must bypass when extended. The wideband wing data only exists if the ADC sees the full HF range — that requires Alex BPF in BYPASS. Same constraint as before. Per pan: "extended mode on" = "this pan's ADC needs BYPASS". AlexController's hybrid policy already handles this — same trigger as the separate wideband pan would have caused.

● Bin density discontinuity at the boundary. Listenable region is ~375 Hz/bin, wideband wings are 7.5 kHz/bin (20× coarser). The trace visibly jumps in resolution at the boundary. We mitigate with: subtle visual treatment (different stroke weight / opacity) so it reads as intentional, not glitchy.

● Refresh rate mismatch. Listenable region refreshes at DDC rate (~50 fps), wideband at 14 fps. The wings update slower than the center. Less jarring than it sounds in practice (your eye attends to the brighter listenable region).

● Per-SKU still gated. Extended-pan capability requires the SKU's wideband path to be wired. P2 boards: straightforward. HL2: needs separate research (different P1 wideband mechanism). So extended pan is "all SKUs" for the listenable behavior (just don't extend out past DDC range) and "P2 SKUs in v1, HL2 follow-on" for the wideband extension.

● Per-pan toggle for the extension. Operator can disable wideband extension on a specific pan if they want the BPF protection for weak signal work. Default: extension on. Right-click pan → "Extended view" toggle.

What this changes about Q7 and the design

● The "12h" layout loses its wideband-specific role. It becomes "wide + 2" for any general use (3-pan vertical with a featured top pane). Wideband is now a property of every DDC pan, not a separate pan type.

● Per-pan source picker simplifies. "DDC pan (Slice A/B/C/D/E)" only. No "Wideband ADC0/ADC1" option in the source menu. Wideband enable is implicit (driven by whether any pan is zoomed out past its DDC range).

● CmdRx packetbuf[23] wideband enable mask: bit N set when any pan is extended on ADC N. Automatic.

● Bench matrix gains rows: zoom-out transitions, click-in-wing tunes correctly, BPF bypass triggers on extension enable.
