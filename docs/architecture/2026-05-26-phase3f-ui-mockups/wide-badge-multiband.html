Multi-band on same ADC → per-pan WIDE badge

Your scenario: 20m slice on ANT1, add a 40m slice on ANT1. What happens to filtering and what does the operator see?

Step-by-step walkthrough

Slice A on 20m (ANT1) — then operator adds Slice B on 40m (also ANT1)
Before:
  Slice A → 14.225 MHz → DDC2 → ADC0 → ANT1
  Alex0 BPF = 20m (filtered, good OOB rejection)
  Pan showing Slice A: no WIDE badge

Operator clicks "+ RX" on a pan, picks 40m for Slice B:

Codec decision:
  Slice B needs a DDC. Routing options:
    a) DDC3 → ADC1 (different ADC, no BPF conflict) ← preferred if 2-ADC board
    b) DDC3 → ADC0 (same ADC, BPF conflict) ← only option if 1-ADC board, or if operator routed via Setup

If 2-ADC board (G2-class):
  Slice B → DDC3 → ADC1 → ANT1 (auto-distributed to second ADC)
  Alex1 BPF = 40m (filtered)
  Alex0 BPF stays 20m (Slice A still filtered)
  Pan A: no WIDE badge
  Pan B: no WIDE badge
  # both slices filtered, both bands clean

If 1-ADC board (HL2 / Hermes) — or 2-ADC with both slices forced to same ADC:
  Slice B → DDC1 → ADC0 → ANT1 (same ADC as Slice A)
  AlexController.recomputeBpf(ADC0) fires:
    uniqueBands = {20m, 40m} → 2 bands → can't filter both
    state.effective = BYPASS
    state.reasonText = "BYPASS (multi-band: 20m + 40m)"
  Pan A: WIDE badge appears top-right
  Pan B: WIDE badge appears top-right
  # both slices unfiltered, both potentially see OOB signals/noise

Visual design choices for the badge

Color: warm amber (#a87a3a background, #c89a5a border). Distinct from the slice letter badge (which uses the slice's color) and from the TX badge (red). Amber says "caution, not alarm" — it's a warning, not a danger.

Placement: top-right of each affected pan, in the title bar row, immediately after the slice letter badge. Always visible when active, never blinks.

Tooltip: hover reveals reason (multi-band / operator / extended / wideband). Text is verbatim from AlexAdcState::reasonText so operator and design doc stay in sync.

Click behavior: click the badge → opens the Alex Filter Policy popup (set Auto / ForceFilter / ForceBypass for this ADC). Lets operator override the auto behavior right from the pan.

Bottom banner: still shows the per-Alex state ("Alex0: BYPASS (multi-band)") for redundancy and quick whole-radio scan. Both surfaces tell the same truth.

Edge cases I want to call out

E1. Operator removes Slice B (40m). AlexController recomputes ADC0: only 20m remains. BPF re-engages on 20m. WIDE badge clears from Pan A. No friction, just disappears.

E2. Operator retunes Slice B from 40m back to 20m. Now both slices on 20m → recompute → 1 band → BPF re-engages. WIDE badges clear from both pans.

E3. 2-ADC board, operator forces both slices to ADC0 via Setup → DDC Routing override. Codec respects the override, AlexController fires recompute, both pans get WIDE badge with tooltip "Alex BPF bypassed — multi-band on ADC0 (20m + 40m). Reduced out-of-band rejection." Operator sees the consequence of their routing choice clearly.

E4. Operator zooms one pan out to extended view (wideband wings). That pan's badge appears with tooltip "extended pan active on ADC0". The OTHER pan on ADC0 also gets the WIDE badge (BPF is bypassed for the whole ADC, affects every DDC on it). Both pans show why.

E5. Operator clicks WIDE badge → popup: "Alex Filter Policy ADC0: [Auto ✓] [Force Filter] [Force Bypass]". Operator picks Force Filter. Auto recompute is suppressed; BPF engages to (say) the TX-bound slice's band. WIDE badge stays visible but tooltip changes to "BPF forced (operator) — non-band slice may see attenuation." Different message, but still warns.

Locking in: WIDE badge per pan, follows the ADC, click → policy popup. Pan title bar gets: slice letter badge · [TX badge if TX-bound] · [WIDE badge if BPF bypassed]. Bottom banner echoes for whole-radio glance. Matches Policy D semantics, just gives operators a much clearer per-pan visual cue.
