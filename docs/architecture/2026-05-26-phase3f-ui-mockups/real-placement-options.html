Source-first audit: where chain/WIDE indicators can actually live

I was drawing a pan title bar that doesn't exist. Here's what the app actually has, then three honest placement options that fit within the real chrome.

What's actually there in MainWindow today

SpectrumWidget — fills the pan area, NO title bar widget. Status text painted via drawTextOverlay(p, specRect, OverlayPosition) in corners:
  • FPS counter — top-right, painted text
  • Peak value display — bottom-right or operator-configurable position

SpectrumOverlayPanel — floating widget on TOP-LEFT of spectrum:
  • Collapse button (◀/▶) at (kPad, kPad)
  • 10 stacked menu buttons (BAND, ANT, Display, Filter, Noise, Spots, Tools, VAX, etc.)
  • Flyout sub-panels that expand to the right when buttons click
  • Button size: kOverlayBtnW=68 × kOverlayBtnH=22 from StyleConstants

VfoWidget — separate widget, the slice flag (frequency, mode, filter, AGC, RIT/XIT, slice color badge). Lives docked or floating, not on the pan.

Bottom status bar (46px, packed):
  LEFT: BandStack icon · +PAN (NYI Phase 3F placeholder) · ☰ Panel toggle · TNF · CWX · DVK · FDX · | · Radio model/fw · | · RxDashboard (slice 0 badges) · PsaIndicator
  CENTER: StationBlock (connection status + name, click to open ConnectionPanel)
  RIGHT: stacked indicator pairs (CAT, etc.) via makeIndicator() helper, 60px wide each

No per-pan title bar exists. No corner widget for status badges. New visual surfaces for chain/WIDE/TX need to fit in one of the above spots or be a brand-new widget.

Three honest options for slice / chain / WIDE indicators

Option A: Extend drawTextOverlay — paint badges as text in top-right corner

◀
BAND
A 14.225 USB · ANT1 · CH 0 TX WIDE 60 fps
Pros: Zero new widgets. Reuses existing drawTextOverlay() mechanism. No layout disruption. Operator's eye is already trained on top-right for FPS, status reads naturally there.
Cons: Painted text isn't clickable — operator can't click WIDE to open Filter Policy popup. Hover tooltips harder to wire. Visual treatment is bare text, no nice pill badges.
Fit: matches existing pattern (FPS, peak value already painted). Smallest implementation.

Option B: Mirror SpectrumOverlayPanel on TOP-RIGHT as a small status overlay widget

◀
BAND
A 14.225 USB CH 0 TX WIDE
60 fps
Pros: Mirrors existing SpectrumOverlayPanel pattern (just on the other side). Clickable WIDE badge → opens Filter Policy popup. Real Qt widgets with hover/tooltip. Visual treatment matches existing chrome (rgba background, rounded border).
Cons: New widget class (SpectrumStatusOverlay?). Eats horizontal space when expanded (must collapse gracefully when pan is narrow). FPS text needs to relocate below or merge into the widget.
Fit: consistent with existing chrome. Most operator-friendly.

Pros: Spectrum stays clean (no chrome on pan). Uses the EXISTING +PAN placeholder (already there waiting for Phase 3F). Chain state visible from anywhere via status bar. Matches the stacked-indicator pattern already used for CAT/TCI.
Cons: Chain state isn't per-pan — operator sees CH 0 / CH 1 globally, not "this pan is on CH 0". Requires looking at status bar to know if your pan is filtered or WIDE. Less immediate than Option A or B.
Fit: uses existing Phase 3F placeholder. No new pan-side widget.

My honest recommendation

Option B + Option C combined.

On each pan (Option B): a small SpectrumStatusOverlay widget in the top-right of every SpectrumWidget. Shows: slice letter badge, freq, mode, CH N, TX (if TX-bound), WIDE (if BPF bypassed). Clickable. Mirrors the existing SpectrumOverlayPanel on the left.

In the bottom bar (Option C): the +PAN placeholder gets activated. Clicking +PAN ▾ opens a menu to add a slice or change layout. Adjacent stacked indicators show per-chain summary (CH 0 / CH 1 with state). This is the "all chains at a glance" view for operators with multiple pans.

Both surfaces. Per-pan badge for "this pan's state", bottom bar for "all chains overview". Different jobs, both useful.

Option A alone (painted text only) loses too much (no clickability). The combined B+C is what fits the existing chrome best.

Push back on the placement honestly. If B is too much new widget surface, or if you'd rather all of this go in the bottom bar (C alone), say so. The source-first read shows where the real seams are.
