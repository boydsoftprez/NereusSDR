Do we actually need wideband if we already have multi-slice DDC pans?

Honest assessment. The case for wideband gets weaker as slice count goes up. It might be worth dropping or deferring.

What you can already do with DDC pans (no wideband needed)

On a G2 (5-slice cap), each DDC pan can show up to 1.5 MHz of spectrum (at 1536 kHz sample rate). With 5 slices:

  Slice A pan: 1.5 MHz of 20m  # entire 20m band fits
  Slice B pan: 1.5 MHz of 40m
  Slice C pan: 1.5 MHz of 80m
  Slice D pan: 1.5 MHz of 17m
  Slice E pan: 1.5 MHz of 15m

Total: 7.5 MHz of cumulative spectrum visible, all listenable, at fine resolution (~375 Hz/bin).

Compare wideband: 61.44 MHz visible at 7.5 kHz/bin (20× coarser), no audio.

For G2-class operators, 5 DDC pans cover most needs. Wideband is mostly redundant.

The cost

Estimated implementation: 1-2 weeks inside 3F. Separate code path for the lifetime of the project.
Bench risk: Thetis built the protocol path but never publicly surfaced the UI — undocumented firmware quirks possible.
Per-SKU support: P2 boards straightforward (same protocol). HL2 / standard P1 boards use a different mechanism we'd have to research separately. So "wideband on HL2" (where it's most valuable) is actually the hardest port — and gated on additional research.
Maintenance: wideband panadapter is a distinct pan type with its own FFT, its own SpectrumWidget mode, its own per-pan source picker option. All future panadapter work has to handle the wideband variant.

Three honest options

A

Defer wideband to a 3F-W follow-on phase

3F MVP ships with: multi-slice (5), multi-pan layout templates, AetherSDR overlay model, Alex hybrid filter policy, TxSliceArbiter, full DDC pan capability. Design the architecture to leave a clean seam for wideband (PanadapterType enum gains Wideband variant later). Ship 3F, get bench feedback, then decide if wideband-W is worth the effort.

Pros: Smaller 3F. Faster to ship. Real operator feedback informs whether wideband is needed. HL2 wideband (the most valuable case) gets proper research time. AetherSDR doesn't have wideband — we're already shipping more than parity with multi-slice + multi-pan alone.
Cons: Loses the "headline feature" of wideband + the "12h layout for wideband" narrative we were building. HL2 operators wait longer for the multi-band view that helps them most.

B

Build wideband as planned in 3F

1-2 weeks of additional 3F scope. Per-ADC wideband enable, "12h" layout, click-to-tune integration with active DDC. P2 boards first, HL2 sub-task gated on protocol research.

Pros: Single epic delivers everything. HL2/HermesII operators get high-value feature. Showcases unused OpenHPSDR capability that Thetis abandoned.
Cons: Bigger 3F. Risk if undocumented firmware quirks surface. Most G2 operators (the bulk of the user base) get marginal value.

C

Drop wideband entirely

5 DDC pans + 1.5 MHz max bandwidth per pan covers most needs. Wideband becomes a permanent "out of scope" for NereusSDR. Save the engineering effort for elsewhere (3M-2 CW TX, 3F polish, bench bugs).

Pros: Zero ongoing maintenance burden. Code stays focused. Most operators won't notice (Thetis users never had it either).
Cons: HL2/HermesII operators lose a feature that would meaningfully help them. We leave OpenHPSDR hardware capability on the table indefinitely. Closes a door we'd want to open later anyway.

Honest recommendation: A (defer to 3F-W follow-on). 3F is already huge — multi-slice + multi-pan + Alex policy + TxSliceArbiter + 8 architectural decisions. Adding wideband is 1-2 more weeks. Defer, ship 3F, gather operator feedback, then make the wideband call with real-world signal on whether HL2/HermesII operators actually want it before we commit to a separate code path.

Your call. You said earlier you wanted wideband in this epic — but the question you just asked is the right one to ask before committing.
