Q6: VFO A/B and split — per-slice, none, or via second slice?

SSB DX work depends on "TX up 5 kHz from RX". RIT/XIT handle Hz-scale shifts. Split handles kHz-scale shifts. Question: how do we expose the kHz-scale capability in a 5-slice world?

What's in place today (audited)

NereusSDR SliceModel.h:
  Q_PROPERTY(double frequency ...)  // one VFO per slice
  Q_PROPERTY(int ritHz ...) + ritEnabled  // already works, Hz-scale RX offset
  Q_PROPERTY(int xitHz ...) + xitEnabled  // already works, Hz-scale TX offset
  // no vfoB, no splitEnabled

RadioModel.h:1213
  Q_INVOKABLE void setSplit(int rx, bool on);  // stub, "currently returns false"

VfoWidget.h: no vfoB / split UI fields. Single-line freq display.

AetherSDR SliceModel.h: no vfoB / split properties. AetherSDR doesn't formalize split.

Thetis console.cs: global chkVFOSplit checkbox; VFOA = RX1 freq, VFOB = TX freq when split (dual-purpose: VFOB also = RX2 freq when multi-RX not in split).

Three approaches

A

Per-slice VFO A/B + per-slice split toggle (Thetis flag pattern, multi-slice)

Each slice gains vfoBFrequency + splitEnabled. When the slice is TX-bound AND split is on, TX uses VFOB. Other slices unaffected. Existing single-frequency users see no change (split off by default).

Slice A: VFOA = 14.225 (RX)   VFOB = 14.230 (TX, split)  [SPLIT]  [TX]
Slice B: VFOA = 7.150 (RX only)   VFOB = —   (split off)

VFO flag UI when split is on (compact two-line):
  ┌──────────────────────────┐
  │ A  14.225.000 USB   ↑R │
  │ B  14.230.000 USB   ↑T │
  └──────────────────────────┘

Right-click VFO flag → {Split toggle · Swap A/B · B = A · Clear B}

Pros: Operator muscle memory from Thetis (SSB DX work expects this). Per-slice split = different slices can be in split or not independently. SliceModel additions are clean (2 properties + signal). Wire format: TX-bound slice's effective TX freq = (split ? vfoB : frequency) + xitHz when xit on. No conflict with RIT/XIT.
Cons: VFO flag UI grows (two-line when split) — needs careful design to not feel cluttered. Persistence schema gains SliceX_VfoBFrequency + SliceX_SplitEnabled per band.

B

No formal split — operator creates a second slice for kHz-scale TX offset

Drop the split concept entirely. For SSB DX: operator creates Slice A (RX at 14.225) and Slice B (TX-bound at 14.230). TxSliceArbiter handoff between them. RIT/XIT continue to handle Hz-scale offsets within one slice.

Pros: Zero new properties on SliceModel. AetherSDR-faithful (they don't formalize split either). Conceptually clean: each frequency is its own slice. TX handoff already in design (TxSliceArbiter).
Cons: Breaks Thetis operator muscle memory. SSB DX needs frequent up/down adjustments; doing this by retuning the TX-bound slice (vs flipping VFO A↔B with one tap) is more friction. Consumes a slice budget for what's traditionally been "one knob". HL2 operators (1 slice cap) literally cannot do split.

C

Global split toggle using next-letter slice as TX (Thetis-faithful, hybrid)

One global Split mode. When active: TX-bound slice's freq = RX, the slice immediately after it (alphabetically) becomes the auto-TX freq. So Slice A in split → Slice B is the TX freq.

Pros: Reuses slice infrastructure, no new properties.
Cons: Couples TX behavior to slice ordering (confusing). Slice B can't be a normal RX slice while split is on (its role flips). Same HL2 problem as Option B. Worst of both worlds.

Worked example — SSB DX pile-up workflow

Option A (per-slice VFO A/B)
1. Tune Slice A to 14.225 (DX station)
2. Right-click → Split → On
3. Slice A's VFO B appears = 14.230
4. Click VFO B → spin wheel → 14.232
5. Push-to-talk → TX at 14.232
6. DX moves to 14.227 — adjust VFO A only
7. Right-click → "B = A + 5 kHz" macro → done

# 1-tap workflow, classic Thetis pattern
Option B (no split — separate slices)
1. Tune Slice A to 14.225 (DX, RX)
2. "+RX" → Slice B
3. Tune Slice B to 14.230
4. Right-click Slice B → "TX bind" (TxSliceArbiter)
5. Adjust Slice B for TX freq via wheel
6. Push-to-talk → TX at Slice B's freq
7. DX moves to 14.227 → adjust Slice A only
   (Slice B's freq stays where you left it)

# 4-tap workflow per slice creation,
# consumes one slice + slice-create churn each DX session

Per-band persistence under Option A

Per-slice per-band schema additions:
  SliceA_Band_20m_Frequency = 14225000  // existing (VFO A)
  SliceA_Band_20m_VfoBFrequency = 14230000  // new
  SliceA_Band_20m_SplitEnabled = True  // new
  SliceA_Band_40m_VfoBFrequency = 7180000  // independent per band

Effective TX freq when TX-bound + split on:
  txFreq = vfoBFrequency + (xitEnabled ? xitHz : 0)
Effective RX freq always:
  rxFreq = frequency + (ritEnabled ? ritHz : 0)

Edge cases for the spec

E1. Slice A split-on, then operator binds TX to Slice B. Slice B's split state independently applies. Slice A still has split state but it's irrelevant until A is TX-bound again.

E2. Split on, slice retunes VFO A across band boundary (20m → 40m). VFO B freq follows the per-band memory load — Slice A on 40m may have different VFOB stored.

E3. XIT and split both on. XIT applies on top of VFO B (TX = vfoB + xitHz). Documented behavior, possibly belt-and-suspenders, operator's call.

E4. Operator hits "B = A" macro mid-MOX. Drop MOX (RF safety), apply the change, allow re-key. Same MOX-drop guard pattern as TxSliceArbiter handoff.

E5. Pan auto-center on VFO B as well as VFO A? Tracking the active slice freq we already do; in split mode there are two flag positions on the pan. Both should render (different colors? one solid, one outline).

My recommendation: A (per-slice VFO A/B + per-slice split). SSB DX work is the canonical use case for split, and the Thetis tactile pattern (tap to flip A↔B, dedicated VFO B knob) is muscle memory we shouldn't break. Existing RIT/XIT continue handling Hz-scale offsets — split fills the kHz-scale gap cleanly. Per-band persistence is symmetric.
