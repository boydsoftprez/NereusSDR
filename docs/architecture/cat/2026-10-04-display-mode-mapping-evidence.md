# CAT display and mode mapping evidence

Source baseline: Thetis v2.10.3.15 (`3759d096`), `Project Files/Source/Console/CAT/CATCommands.cs`. Initial audit against Nereus `e342467fb`; rechecked on Core Controller candidate `27716f5d` on 2026-10-04. The named common modes remain 00..11; no automatic enum cast is permitted.

`MD:566` uses `KString2Mode:9953` / `Mode2KString:9996`. Kenwood codes are explicit named mappings; input 8 passes the handler range and falls through to USB. `DigitalReportsSideband` changes codes 1/2 to DIGL/DIGU on set and reports DIGL/DIGU as 1/2. Retain these source semantics on the bound primary slice. `ZZMD:3949` uses `String2Mode:9856` / `Mode2String:9901`, the named 00..11 table. `ZZME:3971` rejects 08 and otherwise uses its own source switch: unknown width-valid codes silently leave secondary mode unchanged. Nereus modes are declared in `src/core/WdspTypes.h:168`; RADE_U/RADE_L are additional modes and have no Thetis wire code. Query them as unavailable rather than casting integers.

`ZZML:4209` enumerates source DSP modes, formatting name plus two-digit mode code and colon with seven-character left padding. Adapt this to the common named modes 00..11; do not append Nereus-only RADE codes to a Thetis enum namespace. This describes model mode selection, not a new DRM decoding engine.

`CATCommands.cs:56-58` has `NCATInit=500`, `NCATtime=50`; `IF:317` and `MD:566` sleep for the first 500 shared requests. The Nereus service omits this GUI-thread polling delay, documenting that pacing adaptation. It preserves command order and bytes; no Qt main-thread sleep or invented asynchronous startup state is needed.

Display commands `ZZDA:1937`, `ZZDM:2170`, `ZZDN:2242`, `ZZDO:2273`, `ZZDP:2305`, `ZZDQ:2336`, `ZZDR:2367`, `ZZPD:5595`, `ZZPE:5602`, `ZZPO:5690`, `ZZPY:5731`, `ZZPZ:5757`, `ZZZT:8563` operate on Console/Setup display controls. Thetis ZZDM has a corrected explicit display-mode mapping; its author comments must be retained in any future port. Current `PanadapterModel` contains grid storage and per-band station-setting reload APIs, but searching production GUI use finds only widget→model range updates at `MainWindow.cpp:14392-14401`; no `levelChanged` or `gridStepChanged` subscription drives the rendered widget. New `RadioModel::applyPanGridSetting` (`RadioModel.h:1275`) reloads model grid state; it does not supply a CAT display target or rendered-widget control path. The daemon has no client pan display to operate. Other zoom/pan/peak/waterfall state is widget-owned. Therefore these commands are unavailable in this window-independent CAT service (`?;` for every allowed form, no mutation). Merely changing stored PanadapterModel values would not satisfy actual display control. Wiring that broader display ownership is separate work.
