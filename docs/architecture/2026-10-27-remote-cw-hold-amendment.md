## Proposed activity and liveness contract

A remote CW activity belongs to one authenticated station holder and one activity epoch, independent of MOX and individual dots. Its lifetime covers queued text, memory playback, hang, repeat gaps and held Key. A repeat gap must not disarm the watch. Activity ending must not disarm a concurrent mic/program/TUNE activity owned by the same holder; ending another transmit source must likewise not disarm CW. Aggregate eligible activity supplies one consistent owner/epoch decision to the existing liveness machinery, rather than competing timers that clear each other's state.

Admit the activity only after existing permission and CW gate checks succeed. Bind all subsequent keepalives, hold/recovery decisions and completion/stop events to the current owner and epoch. An old command response, duplicate sequence, ended activity or previous holder cannot refresh or reopen the current activity. The activity survives recoverable hold and ends on completion without repeat, explicit stop, safety cut, owner loss, mode/gate refusal or teardown. QSK continues without synthesized MOX.

Desktop and phone start the matching liveness lifetime for accepted CW send, memory or Key, even if no other transmit source is active. Send the approved 100 ms keepalive over every open path and deduplicate by sequence. Reuse the established redundant-path and media barriers; do not count a socket pong as keyed liveness. A late success response must not resurrect a locally stopped activity. Continue to accept release/stop while held, and send them through the existing paths.

**Compatibility proposal:** negotiate support for this CW liveness/hold contract before accepting remote CW that can reach RF. A peer lacking the contract gets an update-required refusal for a new on-air CW request. Stop/release, disconnect and local recovery remain usable. No capability name, protocol number, record shape or user wording is assigned here; the builder chooses those within the existing protocol conventions after this behavior is approved. This behavior is now source-approved by the full receipt above; its exact wire representation is proposed in the implementation plan, not an existing guarantee.

## Proposed sender checkpoint semantics

Maintain two time domains: content/repeat progress pauses; monotonic safety deadlines continue. A paused sender must still wake for stop, teardown and held-Key expiry. Existing threads remain in place; no mutex is added to the audio callback and no RX DSP parameter is changed.

The current queue stores parsed element commands, consumes them with `pop_front()`, marks `firstOfChar`, and carries inline speed deltas: C `CwxSender.h:329-338,382-399`, `CwxSender.cpp:744-752`. Retaining only the remaining queue cannot reconstruct a partially sent letter. The proposed checkpoint retains the already-parsed current letter and its effective timing context, plus unconsumed content. Recovery restarts that letter once, without reparsing the whole message or reapplying earlier inline commands. Completed letters are not replayed. A letter is complete when its final key-down element has ended; a hold during its following separator retains the remaining separator rather than replaying the letter. A hold during a dot, dash or internal letter gap restarts that unfinished letter. These are routine checkpoint bookkeeping decisions preserving the approved unfinished-letter restart and completed-letter non-replay; the implementation plan pins and tests the exact boundaries for root technical review.

Freeze the remaining inter-letter, word and repeat gaps when already between letters. Resume their remaining duration rather than resetting the full gap or consuming it during hold. Preserve the existing lead/hang rules without changing their constants: any necessary output lead on recovery precedes the restarted letter, while existing paused content hang resumes as content timing. Do not duplicate character-count accounting or report a new queued character when replaying an already-started letter. Builder may choose internal storage and notification mechanics, but must keep the displayed current character and completion consistent with these rules.

Held Key is a separate gesture, not a letter checkpoint. Its existing expiry continues from the last valid press, including while held for a network fault. Release is accepted during hold. Recovery may restore it only while its owner, epoch and original deadline remain valid; recovery itself does not renew the gesture. Local serial/radio key input is not converted into queued text and is not covered by this replay rule.

The proposed computer sidetone follows the paused sender's audible output: force it low during hold and resume with the checkpoint, so it does not sound a sustained element while RF is suppressed. This UX consequence is now explicitly approved by `evidence/cw-full-source-implementation-approval.json`; the earlier content-only receipt did not establish it by itself.
